# Version plan: 0.6.1 concise consent and priority semantics

- Status: Developer design accepted; runtime implementation not started
- Plan date: 2026-09-22
- Change class: `framework`
- Audience: `both` after implementation; this design revision is developer-only
- Primary ADR: ADR-0015
- Requirements: `DATA-012`, `FLOW-009`–`FLOW-010`, `ENV-003`, `ENV-008`, `FEED-003`, `FEED-009`

## Objective

Reduce ordinary user authorization to one meaningful decision per operation without weakening privacy or project authority. Tool discovery receives one pre-action approval covering detection and private save. Handoff and feedback packaging prepare concise deterministic previews and create final files only after one whole-preview approval. A prior collection approval appears only when new external/private material must be read.

Also clarify, without data migration, that framework load priority, foreground/background task scheduling, and objective/milestone/task hierarchy are separate concepts.

## Completion standard

v0.6.1 is complete only when a user can:

1. receive one concise tool-discovery explanation, approve once, and have the minimal private profile detected and saved without a second confirmation;
2. request a handoff—or let the framework detect the trigger—review one package preview, approve once, and obtain a verified `.llmpack` whose exact content matches the approved preview;
3. reject or withhold approval and observe that no final package is created;
4. submit ordinary framework feedback with one preview approval, while feedback needing new private/external reads uses exactly one additional bounded collection approval;
5. integrate `.llmpack` content only through the existing itemized proposal/commit process;
6. verify and triage both v0.6.0 and v0.6.1 feedback packages;
7. understand that `high`/`low` task priority is scheduling, not goal importance or time horizon.

## Implementation sequence

1. Add synthetic feature-contract tests for the ten ADR-0015 validation cases.
2. Add canonical package-preview generation and preview-hash comparison helpers.
3. Implement one-operation environment initialization while preserving legacy profile reads and diagnostic commands.
4. Add `.llmpack` preview and approval-bound export without changing package format v1.
5. Add ordinary/extra-collection feedback preview flows while retaining feedback package v1 and developer intake compatibility.
6. Update runtime high-priority rules and conditional references, including priority semantics.
7. Run the full invariant, feature, skill, generated-child, compatibility, and whitelist-release gates.

Tests are based on the accepted general framework requirements in ADR-0015 and use new synthetic fixtures. They must not copy, retain, paraphrase into fixtures, or depend on the two external one-shot feedback packages.

## Compatibility

- Total-skill shared-runtime update; existing compatible children need no adapter rewrite.
- Entry protocol remains 1.
- Project state, task board, record store, source registry, project-map, and index schemas remain unchanged.
- `.llmpack` remains `llm-long-term-project-handoff/v1`.
- `.ltpm-feedback` remains `ltpm-framework-feedback/v1` and old packages stay readable.
- Existing private machine profiles stay readable; new observation status is additive and does not change project data.

## Non-goals

- automatic upload or developer submission;
- cryptographic proof that a human approved a preview;
- package authenticity signatures;
- project-data schema migration or child adapter changes;
- replacing itemized integration decisions with package-level acceptance;
- broad hardware benchmarking or recursive machine inventory;
- parallel exploration merge;
- changing the persisted `high`/`low` task-priority values.

## Release decision

This turn authorizes developer-mode design only. Runtime implementation, installation update, `main` replacement, tag, and GitHub Release require subsequent work and separate stable-release approval.
