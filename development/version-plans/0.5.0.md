# Version plan: 0.5.0 project isolation and thin child runtime

- Status: Released as `v0.5.0` on 2026-09-22
- Plan date: 2026-09-21
- Change class: `framework`
- Audience: `both` (developer implementation and runtime-user behavior)
- Data boundary: no real project, regression, evaluation, private-user, or machine-profile data enters the repository
- Primary ADR: ADR-0013
- Requirements: `PROD-006`, `PROD-009`, `CHILD-004`–`CHILD-009`, `CHILD-011`, `ISOL-001`–`ISOL-006`, `ENV-006`

## Release objective

Make one installed total skill safely serve multiple unrelated project-local child skills. A child becomes a thin project adapter and durable data instance rather than a copied framework fork. Ordinary conversations bind to one project, all formal operations fail closed on identity or compatibility ambiguity, and existing v0.4.0 children receive an explicit, recoverable upgrade path.

## User-visible completion standard

The version is complete only when a user can:

1. create two unrelated child skills under separate project roots;
2. invoke either child and see its project identity and binding reported;
3. search, explore, package, integrate, and commit within one project without any result or state from the other;
4. receive an explicit stop/switch response when attempting to use another project in the same ordinary conversation;
5. update the installed total skill and continue using compatible children without rewriting project records or work;
6. inspect an old or incompatible child safely, receive an itemized upgrade/migration proposal, and apply only accepted changes;
7. validate the upgraded child and receive separate framework-upgrade and data-migration receipts when both are needed.

## Proposed scope

### 1. Introduce the project instance contract

Replace the current minimal `framework/version.json` role with `framework/instance.json` using a new versioned schema. It records:

- immutable `project_id` and child skill name;
- canonical manager skill name;
- entry-protocol version and supported compatibility range;
- creation framework release and last migrated release;
- project-data schema versions;
- framework-owned adapter file hashes and ownership declarations.

The contract does not store a mutable global current project and does not absorb project facts or private environment data.

### 2. Generate thin child skills

Update the initializer and template so newly generated children contain:

- a concise explicit-only `SKILL.md` that identifies and binds the project, loads its map, and delegates shared protocols to the total skill;
- `framework/instance.json`;
- a user-owned `project-instructions.md` preserved across framework upgrades;
- the existing project-local `state/`, `records/`, `sources/`, `work/`, `views/`, `index/`, and `packages/` stores.

Stop copying shared `framework/conditional/*.md` modules into new children. Keep domain/project instructions out of framework-owned adapter files.

### 3. Add compatibility and binding checks

Add a deterministic inspection/check command used before formal operations. It resolves one project-skill root and verifies:

- expected and observed `project_id`;
- canonical root and child-skill identity;
- entry-protocol and data-schema compatibility;
- internal ID/revision consistency;
- managed adapter hashes and unexpected modifications.

The command returns explicit `compatible`, `upgrade-required`, `migration-required`, `ambiguous`, or `invalid` states. Only `compatible` permits ordinary formal writes. Other states remain inspectable and fail closed for commit or migration actions.

Every existing tool keeps or gains an explicit project-skill-root argument and performs the shared binding check instead of relying on a global current project.

### 4. Add conversation binding rules

Add a high-priority runtime invariant:

- the first explicitly invoked child establishes one active project for ordinary work;
- responses that can affect project state identify the project name and `project_id`;
- a second child invocation does not silently switch;
- the framework requests an explicit switch or recommends a new conversation;
- it states that authority isolation cannot erase text already loaded in the conversation.

This release will not attempt to persist a global session selector on disk.

### 5. Provide a v0.4.0 child upgrader

Implement inspect, propose, apply, and verify stages:

1. inspect the child read-only and produce an upgrade plan;
2. classify each affected file as framework-owned, project-owned, derived, or unknown;
3. present itemized framework-adapter changes and any separate data migrations;
4. require user acceptance before writing;
5. stage changes and validate the candidate;
6. atomically publish or restore the original files;
7. emit an architecture-upgrade receipt;
8. if schemas change, run a distinct accepted project-data migration and emit a separate receipt/revision result.

Unknown modifications are never overwritten automatically. The v0.4.0 copied conditional modules may be archived or removed only as an explicitly accepted framework-owned cleanup.

### 6. Add explicit cross-project coordination foundation

The initial v0.5.0 behavior is proposed as **read-mostly**:

- the user must explicitly name the participating child skills;
- the coordinator reads compact maps first and reports project IDs, searched scope, and exclusions;
- no combined formal transaction exists;
- proposed writes are emitted as separate per-project proposal sets and must be committed from their respective bound project contexts.

Whether one coordination conversation may orchestrate those separate commits remains an approval question and is not required for the isolation core.

### 7. Extend validation and automated tests

Add a seventh invariant group for multi-project isolation while preserving the existing six groups. Synthetic temporary projects will cover:

- A-only retrieval and B-only retrieval;
- root/ID mismatch and duplicate/ambiguous resolution;
- cross-project handoff rejection;
- no global project-state writes;
- compatible total-skill refresh without project-data mutation;
- preservation of `project-instructions.md`;
- read-only behavior under incompatible protocols;
- v0.4.0 upgrade rollback and receipts;
- explicit cross-project mode and separate proposal sets;
- release bundle generation of two independently usable children.

Real project material and historical failures remain external under the existing regression/evaluation policy.

### 8. Release and documentation work

- advance development schemas and framework prerelease version;
- update runtime references, framework map, bootstrap flow, templates, validators, and user README;
- update the exact runtime allowlist for every new runtime file;
- write prerelease notes and a release candidate note;
- run the complete developer and release gates;
- publish `main`, tag, archive, and release receipt only after a separate release approval.

## Proposed implementation sequence

1. Schema and fixture design: instance contract, compatibility result, upgrade plan, and receipts.
2. Read-only inspector and binding library.
3. Thin initializer/template and preservation boundary for project instructions.
4. Tool integration so every formal operation uses binding checks.
5. v0.4.0 staged upgrader and separate data-migration route.
6. Conversation-binding and read-mostly coordination protocols.
7. Isolation/regression tests, release tests, documentation, prerelease notes, and candidate bundle.

Each stage must leave the test suite passing. Schema or behavior changes discovered during implementation require product-map reconciliation and, when architectural, an ADR amendment or new ADR rather than an undocumented deviation.

## Explicit non-goals for 0.5.0

- parallel exploration package merge;
- ChatGPT web support;
- automatic private machine-profile refresh;
- signed packages;
- a global personal knowledge base;
- background discovery or automatic mutation of every local project;
- perfect semantic erasure after two projects have already been loaded into one model context;
- multi-project atomic transactions;
- domain-specific education safety suites.

## Compatibility and rollback proposal

- New children use the thin instance contract.
- Existing v0.4.0 children remain readable before upgrade.
- Formal writes through the new total skill require either confirmed compatibility or an accepted upgrade.
- Architecture upgrades stage a complete recoverable copy of every changed framework-owned file and publish atomically.
- Project-data migration is not bundled into architecture publication; if it fails, the architecture upgrader must either remain compatible with the old data schema or roll its own changes back.
- No project-owned instruction, record, source, task, exploration, artifact, package, or receipt is deleted during automatic cleanup.

## Risks and controls

| Risk | Control |
|---|---|
| Thin children fail when the global skill is missing | Detect the missing manager, report exact dependency, and allow data inspection without formal writes. |
| Framework upgrade silently changes accepted facts | Treat project data as user-owned and require a separate migration transaction. |
| Same conversation carries semantic residue from another project | Explicit binding, no silent switch, and new-conversation recommendation. |
| Multiple children have the same display name | Bind on immutable project ID and canonical root, not display name. |
| User edited a managed adapter file | Hash detection and itemized conflict proposal; never overwrite unknown edits. |
| Cross-project comparison becomes a hidden merge | Read-mostly coordination plus separate proposals, revisions, and receipts. |

## Approved decisions and release result

The user approved implementation on 2026-09-21 and explicitly approved stable publication on 2026-09-22. The release updated `main` only from the validated whitelist artifact, created stable tag `v0.5.0`, and published the matching GitHub archive. No real child project was migrated and no real/private project data was stored.

Approved choices:

1. **Release scope:** use v0.5.0 for the thin-child and isolation foundation described above.
2. **Dependency model:** require a compatible installed total skill; do not embed a fallback runtime in each child for this version.
3. **Legacy handling:** keep v0.4.0 children readable and require an itemized, user-confirmed upgrade before new formal writes.
4. **Cross-project mode:** ship it as read-mostly; generate separate proposal sets but do not orchestrate multi-project commits in v0.5.0.

Release evidence: 31 deterministic tests passed, including five multi-project isolation tests and three release-bundle tests; development/runtime skills and two generated children validated; the remotely downloaded archive matched SHA-256 `6f1f9dab3ab341faa09ddf51953d5838ba2e4c4d74c6df095975531c9638608b`. See `development/releases/v0.5.0.json`.
