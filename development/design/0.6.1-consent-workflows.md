# v0.6.1 concise-consent workflow design

- Scope: developer-only implementation contract
- Authority: ADR-0015 and user-confirmed requirements
- Runtime status: not implemented in v0.6.0
- Package compatibility: `.llmpack` v1 and `ltpm-framework-feedback/v1` retained

## Shared interaction rule

```text
already authorized context
-> prepare deterministic preview
-> one whole-preview approval
-> create and verify final file

new external/private read required
-> one bounded collection approval
-> collect only that scope
-> prepare deterministic preview
-> one whole-preview approval
-> create and verify final file
```

The preview approval covers the package as one operation. It does not approve upload, external transmission, truth, sender identity, or later formal integration.

## Environment initialization

### User interaction

Present one short pre-action prompt describing purpose, scope, exclusions, and private save location. After approval, run one initialization operation and report results; do not request field-by-field correction or a second save decision.

### Proposed tool interface

```bash
python scripts/environment_profile.py initialize \
  --approved-purpose tool-discovery
```

`initialize` detects and atomically saves `private/local-environment.json`. Calling it without the explicit approved-purpose value fails before discovery. This flag records that the dialogue obtained approval; it is not an authentication mechanism.

Default discovery includes:

- minimal OS/architecture/runtime compatibility;
- presence of known command-line tools without executing them;
- installed skill names from the recognized skill roots;
- local model runtimes and names from bounded known registry locations.

Default discovery excludes:

- credential or environment-variable values;
- arbitrary file contents and unrelated paths;
- recursive scanning of the home directory;
- CPU, memory, accelerator, and broad resource inventory unless separately justified or requested.

New observations use status `detected-with-user-authorization`. Individual capabilities are `discovered`, `verified`, or `unavailable`; command presence begins as `discovered`. Existing schema-v1 profiles and the diagnostic `detect`/explicit `save` commands remain readable and supported.

## Common package preview

Both package workflows expose a compact human summary backed by a canonical machine plan:

```json
{
  "schema": "ltpm-package-preview/v1",
  "package_type": "handoff | framework-feedback",
  "reason": "...",
  "bound_context": {},
  "destination": "/absolute/output/path",
  "included_sections": [],
  "attachments": [
    {"source": "...", "archive_path": "...", "size": 0, "sha256": "..."}
  ],
  "explicit_exclusions": [],
  "local_only": true,
  "automatic_upload": false,
  "source_fingerprints": {},
  "preview_sha256": "..."
}
```

`preview_sha256` hashes the canonical plan without its own hash field. The human-facing display may summarize large section contents, but it must show every attachment, destination, exclusions, package type, reason, and authority boundary.

## `.llmpack` flow

### Proposed commands

```bash
python scripts/handoff.py preview \
  --project-skill /project/.agents/skills/example \
  --handoff /path/handoff-draft.json \
  --output /path/task.llmpack \
  --artifact /source/file=artifacts/name

python scripts/handoff.py export \
  --project-skill /project/.agents/skills/example \
  --handoff /path/handoff-draft.json \
  --output /path/task.llmpack \
  --artifact /source/file=artifacts/name \
  --approved-preview-sha256 HASH
```

`preview` performs read-only binding and size/path/hash checks and emits the plan without creating the output. `export` recomputes the plan and compares its hash before any output-directory or temporary-package write. A mismatch or missing approval fails with no `.llmpack`.

The package format and receiving integration process do not change. Approval authorizes creation only; unpacked `proposed_changes` remain itemized user decisions.

## `.ltpm-feedback` flow

### Ordinary case

Build the preview from current conversation context and user-supplied facts. The final preview includes problem summary, included information, attachments, redactions, exclusions, retention, synthetic-derivative choice, destination, and no-upload statement. One approval creates the package.

The exported v1 issue records the same approval time for `local_collection` and `export`; `local_collection.scope` states that only already authorized current context and supplied material were used. `approved_fields` still lists the v1 internal sections for machine compatibility, but the user approves the preview as a whole.

### Extra-collection case

Before reading any new file, log, environment value, or external/private source, show its bounded purpose and scope and obtain collection approval. Record that earlier event in `local_collection`. After minimization and redaction, follow the ordinary final-preview approval.

### Proposed commands

Add `feedback.py preview` and require `--approved-preview-sha256` on the normal export path. Retain a legacy explicit-v1 export route for existing automated callers that already provide a complete valid v1 consent object; mark it as compatibility behavior rather than the recommended user interaction.

Developer intake continues to verify and triage v1 packages without change. It must not infer whether one or two conversational approvals occurred merely from equal or different timestamps; the declared collection scope is the authoritative audit description.

## Priority-language update

Runtime documentation and initialization displays use these meanings:

| Concept | Stored values | Meaning |
|---|---|---|
| Framework load priority | `high`, `low` | Always loaded versus conditionally loaded rules |
| Task scheduling priority | `high`, `low` | Foreground/current queue versus background/later queue |
| Goal hierarchy | objective, milestone, task, typed relations | What must be achieved and how work is sequenced |

Time horizon alone never sets task priority. A mandatory later milestone remains part of goal hierarchy and gains foreground tasks when its dependencies or schedule make it current.
