# 0.6.0-dev.1

Development implementation of ADR-0014 and the accepted consent-based feedback loop.

## Runtime changes

- A user's own report of a possibly framework-related problem is now an explicit trigger, alongside reusable failures, invariant violations, repeated ambiguity, unsafe allowances, blocked valid actions, and data-loss/privacy risk.
- Cause and remediation are classified provisionally and separately.
- Local evidence collection and exact-scope export require separate consent.
- `.ltpm-feedback` provides a single-file, integrity-checked, manually transferred format distinct from `.llmpack`.
- The runtime never uploads feedback and excludes full conversations, project stores, machine profiles, secrets, and unrelated paths by default.
- Existing compatible v0.5.0 children inherit shared behavior; new children also contain a thin feedback route.

## Developer changes

- External-only intake verifies, safely inspects, quarantines inert packages, creates triage proposals, and emits non-mutating resolution receipts.
- Real feedback remains external. Repository tests use only synthetic, non-reconstructive data after itemized approval.
- Runtime whitelist and release tests cover the new user/developer boundary.

## Validation record

- The first full-suite run found that the release-contract test supplied prerelease text `0.6.0-dev.1` to a builder that deliberately accepts only stable `MAJOR.MINOR.PATCH` versions. No runtime feedback behavior failed. The test was corrected to build candidate `0.6.0` while retaining `0.6.0-dev.1` in development source metadata; the finding is preserved here rather than discarded.
- Final validation passed all 34 deterministic tests, including three synthetic feedback-channel tests and the whitelist release contract, followed by the skill structure validator and diff whitespace check.
