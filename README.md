# LLM Long-Term Project Management

一个面向 Codex CLI 的显式调用 skill，用稳定项目契约、项目本地正式记录、派生地图、覆盖范围明确的检索、探索交接包和用户逐项确认，实现跨对话协作与长期项目管理。

## 安装

将仓库克隆或链接到 Codex 的用户 skill 目录，并确保目录名与 skill 名一致：

```bash
git clone --depth 1 --single-branch --branch main \
  https://github.com/hyhml/LLM_Long-Term_Project_Management.git \
  ~/.agents/skills/long-term-project-manager
```

`main` 由运行时白名单自动构建，只包含用户运行所需内容。架构决策、测试和发布工具位于单独的 `development` 分支；上述单分支安装不会下载这些开发材料。只有框架开发者需要切换到 `development`。

重启 Codex 后显式调用：

```text
$long-term-project-manager 初始化这个项目
```

该 skill 不允许隐式调用。第一次运行会说明工具发现的目的和限定范围；用户批准一次后，才检测可用工具、skill 和本地模型并私有保存。创建项目子 skill 时，也会先展示项目目标、范围、非目标、假设、证据标准、完成标准、项目地图和高低优先级待办，确认后才写入 `.agents/skills/<project-skill>/`。

生成的子 skill 是一个项目本地的薄入口：保存不可变项目身份、项目专属说明和全部项目数据，通用协议与工具则由当前兼容的总 skill 提供。因此更新总 skill 不会重写项目记录；只有入口协议或数据 schema 不兼容时，才会提出逐项升级或迁移方案。

初始化器会报告子 skill 是否位于当前 Codex 工作目录向上的发现路径中。若项目位于当前目录的下级、同级或其他位置，需要从报告的项目根目录启动新对话后再显式调用；框架不会为方便发现而把项目子 skill 复制或链接到用户级 skill 目录。

## 工作循环

1. 整理对话维护稳定项目契约、正式记录、来源、类型化关系和已确认待办，再生成项目地图。
2. 探索对话只执行一个已确认任务，未确认内容留在 `work/`，不修改正式状态或派生视图。
3. 探索对话整理 `.llmpack` 预览，用户整体批准后才生成单文件交接包。
4. 整理对话校验并解包，逐项提出变更。
5. 用户逐项接受、修改、拒绝或暂缓后，通过不可发现的候选数据副本提交一次 revision 并生成回执；旧版本遗留的已提交完整候选只会在预览和批准后清理。

项目检索始终报告已搜索和未搜索的授权范围。空结果只表示在当前覆盖范围内未找到，不代表项目中不存在。

普通对话一次只绑定一个子项目。调用另一个子 skill 时不会静默切换，而会要求明确确认或建议开启新对话。显式的跨项目协调默认只读取各项目的紧凑地图并分别生成提案，不合并项目 authority，也不进行跨项目原子提交。

skill 会把分类作为持续控制：对每个实质工作项判断框架层或数据层、数据子类型以及受众，并据此确定写入权限、存储位置、验证方式、版本路径和发布边界。新分支出现或即将持久化、打包、发布、交接时会重新判断；混合变更先拆分，开发态内容不会被描述成已经发布的运行时功能。

`.llmpack` 的批准绑定预览 SHA-256；内容、项目 revision 或目标路径改变后需要重新批准。包仍使用逐文件 SHA-256 校验完整性，但当前版本不提供发送者身份认证。导入的脚本不会自动执行，打包批准也不等于接受解包后的项目变更。

## 经用户许可的框架反馈

用户在使用子 skill 时主动提出可能与框架有关的问题，会触发初步分类；这只是候选判断，不代表已经确认根因。普通反馈只使用当前已授权上下文，展示脱敏、覆盖范围和完整预览后由用户批准一次即可生成 `.ltpm-feedback`。只有需要额外读取日志、文件或其他私人资料时，才会先增加一次限定范围的读取许可。

反馈文件不会自动上传。用户自行将它交给开发者；它不进入项目正式记录，也不同于跨对话 `.llmpack`。真实案例保留在仓库外，只有另外获准且无法反推原始私密内容的合成复现才能成为框架测试。开发者处理后可以返回不自动修改项目的解决回执，说明最终分类、修复版本以及子 skill 是否需要刷新运行时、升级入口或迁移数据。
